# Copycraft — Техническая документация

## Архитектура решения

Copycraft работает **внутри Claude Code** — без отдельного приложения, без фронтенда, без бэкенда. Рабочее пространство копирайтера = папка проекта + возможности Claude Code.

### Маппинг функций на возможности Claude Code

| Функция Copycraft | Реализация | Компонент Claude Code |
|-------------------|-----------|----------------------|
| Системный промпт | `CLAUDE.md` в корне проекта — компактная инструкция (~4000 токенов) | Загружается автоматически при старте сессии |
| Модульные инструкции | `blocks/` — 10 блоков, загружаются по задаче через Read tool | Read tool (встроен в Claude Code) |
| База знаний (формулы, примеры, материалы) | Файлы в папках `knowledge/` | Read tool (встроен в Claude Code) |
| RAG по большим объёмам данных | MCP-сервер с ChromaDB (векторный поиск по `knowledge/`) | MCP Protocol — настраивается в `.claude/settings.local.json` |
| Внешний ресерч | Встроенный Web Search | Web Search tool (встроен в Claude Code) |
| Стейт-машина (8 стейтов) | Протокол описан в `blocks/02_state_machine.md`, ссылка из `CLAUDE.md` | Claude следует инструкции, состояние хранится в `state.md` |
| Версионность блоков | Git-коммиты с конвенцией `{тип}({проект}): {описание}` | Git (встроен в Claude Code) |
| Обратная связь | `projects/{name}/results.md` — метрики, A/B тесты, выводы | Write/Read tool |
| Обработка тупиков | Deadlock Recovery протокол в `CLAUDE.md` | Автоматический счётчик в `state.md` |
| Экспорт | Запись в нужном формате через Write tool | Write tool (встроен в Claude Code) |
| Критерии качества | Critic Mode (26 вопросов) в `blocks/09_debugging.md` + формальные метрики | Claude проверяет автоматически в STATE=DEBUGGING |
| Рентген текста (X-ray) | Независимый анализ любого продающего текста по XRAY_PROTOCOL_V1 | Блок 10 (`blocks/10_xray.md`) |
| HTML-сборка | Автосборка лендингов и рентген-отчётов для GitHub Pages | `scripts/build_html.py`, `scripts/build_xray.py` → `docs/` |

## Компоненты системы

### 1. CLAUDE.md — системный промпт

Главный файл. Загружается автоматически при каждом запуске Claude Code в этой папке. Содержит:

- **Роль**: копирайтер-ассистент (Direct Response Architect)
- **Протокол запуска сессии**: автоматическое определение проекта, чтение state.md, валидация с пользователем
- **Автозагрузка блоков**: таблица "стейт → блоки", пользователю не нужно помнить номера
- **Обработка тупиков (Deadlock Recovery)**: протокол для Critic FAIL 3+, невнятных правок, пустого ресерча
- **Git-стратегия**: конвенция коммитов вместо папки `versions/`
- **Обратная связь**: формат `results.md` для метрик и A/B тестов
- **Базовые правила**: лимиты, запреты, формат ответов
- **Инструкция по работе с `knowledge/`**: когда и как обращаться к файлам

**Размер**: CLAUDE.md содержит протокол запуска, стейт-таблицу, git-стратегию, X-ray протокол, HTML-сборку и Knowledge Base инструкции. Детальная логика вынесена в `blocks/`.

**Протокол запуска сессии** (ключевое отличие от ручного подхода):
1. Claude читает `projects/` → находит проект(ы)
2. Claude читает `state.md` → определяет текущий стейт
3. Claude показывает статус и спрашивает: "Всё верно? Продолжаем?"
4. Claude автоматически загружает нужные блоки по таблице стейт→блоки
5. Пользователь просто пишет "Продолжаем" — без необходимости помнить номера блоков

### 2. Модульная система блоков (blocks/)

Блоки — это детальные инструкции, разбитые по этапам работы. Загружаются по запросу в начале каждого чата.

#### Карта блоков

| # | Файл | Содержимое | Когда загружать |
|---|------|-----------|-----------------|
| 01 | `01_system_core.md` | Identity, Philosophy, 7 Laws М.О.С., RAG Security | INPUT–STRATEGY, XRAY |
| 02 | `02_state_machine.md` | Стейты, переходы, правила EXECUTION | Все стейты кроме INPUT–RESEARCH |
| 03 | `03_evidence_strategy.md` | Evidence Map + Strategy Skeleton + Proof Plan | STATE=INPUT → STRATEGY |
| 04 | `04_protocols.md` | Operational Loop, Truth Protocol, Query Protocol | STATE=INPUT, QUERY |
| 05 | `05_research_engine.md` | JTBD-фреймворк, матрица Шварца, Unfair Advantage | STATE=RESEARCH |
| 06 | `06_meaning_maker.md` | UM Engine, Big Idea, Offer Engine | STATE=STRATEGY |
| 07 | `07_copywriting_kernel.md` | RMBC, Lead Engine, Story Engine, Mechanism, Product Reveal, Proof Engine, Close | STATE=EXECUTION |
| 08 | `08_asset_library.md` | Шаблоны Email, Ads, VSL, Chatbot | STATE=EXECUTION (для email/ads/vsl/chatbot) |
| 09 | `09_debugging.md` | Critic Mode (26), Launch Checklist (19), Strategy Critic (7) | STATE=DEBUGGING, DELIVERY, STRATEGY |
| 10 | `10_xray.md` | X-ray — рентген-анализ продающих текстов (балл 0–100) | STATE=XRAY (независимый режим) |

#### Принцип загрузки

Блоки загружаются **автоматически** на основе текущего стейта из `state.md`. Пользователю не нужно помнить номера блоков — Claude определяет, что загружать, по таблице в CLAUDE.md:

| Стейт | Блоки для загрузки | ~Токены |
|-------|-------------------|---------|
| INPUT | 01 + 03 + 04 | ~12k |
| QUERY | 01 + 04 | ~8k |
| RESEARCH | 01 + 05 | ~8k |
| STRATEGY | 01 + 02 + 03 + 06 + 09 | ~16k |
| EXECUTION | 02 + 07 (или 02 + 08) | ~10k |
| DEBUGGING | 02 + 09 | ~6k |
| DELIVERY | 02 + 09 | ~6k |
| REVIEW | 02 | ~4k |

#### Типичный workflow по чатам

```
Чат 1: Пользователь: "Новый проект — {описание}"
        Claude: создаёт проект → INPUT + QUERY (блоки загружены автоматически)
Чат 2: Пользователь: "Продолжаем"
        Claude: читает state.md → RESEARCH (блоки загружены автоматически)
Чат 3: Пользователь: "Продолжаем"
        Claude: → STRATEGY (блоки загружены автоматически)
Чат 4–7: Пользователь: "Продолжаем"
        Claude: → EXECUTION (блоки загружены автоматически)
Чат 8: Пользователь: "Продолжаем"
        Claude: → DEBUGGING + DELIVERY (блоки загружены автоматически)
```

### 4. MCP-сервер (RAG)

Кастомный MCP-сервер для семантического поиска по `knowledge/` через ChromaDB.

**Файл:** `scripts/knowledge_server.py`

#### Стек

- **ChromaDB** (persistent) — векторная БД, хранение в `chroma_data/`
- **Embedding-модель** — `paraphrase-multilingual-MiniLM-L12-v2` (локальная, поддерживает русский)
- **MCP SDK** (FastMCP) — протокол связи с Claude Code

#### Зависимости

- Python 3.11+
- `chromadb` — векторная БД
- `sentence-transformers` — локальные эмбеддинги
- `mcp` — Python MCP SDK

#### Настройка

В `.claude/settings.local.json`:

```json
{
  "mcpServers": {
    "knowledge-base": {
      "command": "/Library/Frameworks/Python.framework/Versions/3.11/bin/python3",
      "args": ["scripts/knowledge_server.py"],
      "cwd": "/Users/ilaija/Documents/ my-first-project"
    }
  }
}
```

#### MCP-инструменты

| Инструмент | Описание |
|-----------|----------|
| `search_knowledge(query, n_results=5, category=None)` | Семантический поиск по базе знаний |
| `list_sources()` | Список файлов в базе с количеством чанков |
| `reindex(force=False)` | Переиндексация (по умолчанию только изменённые файлы) |

#### Как работает

1. **При запуске** — автоматически индексирует все `.md` файлы из `knowledge/`
2. **Чанкинг** — разбивает по markdown-заголовкам (`##` и `###`), сохраняет метаданные (источник, секция, категория)
3. **Инкрементальная индексация** — при повторном запуске переиндексирует только изменённые файлы (по MD5-хешу)
4. **Поиск** — принимает запрос на естественном языке, возвращает релевантные фрагменты с указанием источника

### 5. Web Search (встроенный)

Используется для внешнего ресерча. Claude Code выполняет поиск самостоятельно.

#### Когда срабатывает

- **STATE=RESEARCH** — поиск отзывов ЦА, текстов конкурентов, статистики
- **STATE=EXECUTION (RESEARCH-MINI)** — мини-ресерч при нехватке данных перед генерацией блока
- **По запросу пользователя** — "найди данные по рынку X"

#### Ограничения (заложены в CLAUDE.md)

- Результаты поиска показываются пользователю ПЕРЕД вставкой в текст
- Найденные цифры/факты помечаются как "[требует подтверждения]"
- Приоритет: русскоязычные источники → англоязычные
- Данные старше 2 лет помечаются как "⚠ возможно устарело"

## Стейт-машина: техническая реализация

Стейт-машина реализована не в коде, а как **протокол в блоках** (`blocks/02_state_machine.md`). Claude следует инструкции и переходит между стейтами через диалог с пользователем.

### 8 стейтов

```
INPUT → QUERY ──────────────────┐
  │                              │
  ├─ (достаточно данных) ────────┼──→ STRATEGY → EXECUTION ⇄ DEBUGGING
  │                              │                              │
  └─ (Авто-ресерч) → RESEARCH ──┘                      (PASS, все блоки)
                                                               │
                                                           DELIVERY → REVIEW
```

### Как это работает

```
Протокол запуска сессии (CLAUDE.md):

1. Claude читает папку projects/ → находит проект(ы)
2. Claude читает state.md → определяет текущий стейт, фазу, блок
3. Claude показывает краткий статус пользователю:
   ПРОЕКТ: {название}
   СТЕЙТ: {текущий стейт}
   ПРОГРЕСС: {N из M стейтов}
4. Claude спрашивает: "Всё верно? Продолжаем?"
5. При подтверждении — автоматически загружает нужные блоки по таблице
6. Пользователь просто пишет "Продолжаем" — без необходимости помнить номера

При каждом переходе между стейтами Claude:
  1. Проверяет условия перехода из блока 02
  2. Если условия не выполнены — сообщает пользователю
  3. Обновляет state.md
  4. Делает git-коммит с описанием изменения
```

### Формат state.md

```markdown
# Состояние проекта: {название}

## Текущий стейт: EXECUTION
## Фаза: PHASE C (COPY)
## Текущий блок: Story
## Формат: landing

## Пройденные стейты
- [x] INPUT (завершён 2026-02-16)
- [x] QUERY (завершён 2026-02-16)
- [x] RESEARCH (завершён 2026-02-16)
- [x] STRATEGY (завершён 2026-02-16)
- [ ] EXECUTION ← текущий
- [ ] DEBUGGING
- [ ] DELIVERY
- [ ] REVIEW

## Блоки EXECUTION
| Блок | BRIEF | COPY | DEBUGGING | Статус |
|------|-------|------|-----------|--------|
| Lead | ✅ | ✅ | PASS | APPROVED |
| Story | — | in progress | — | pending |
| Mechanism | — | — | — | pending |
| Product Reveal | — | — | — | pending |
| Offer | — | — | — | pending |
| Proof | — | — | — | pending |
| Close | — | — | — | pending |

## Счётчик попыток
| Блок | Попыток FAIL | Последняя причина |

```

### Правила переходов

| Переход | Условие |
|---------|---------|
| INPUT → QUERY | MISSING INFO ≥ 3 — нужны уточняющие вопросы |
| INPUT → STRATEGY | Данных достаточно — QUERY пропускается |
| INPUT → RESEARCH | Пользователь выбрал "Авто-ресерч" |
| QUERY → STRATEGY | Пользователь ответил на вопросы |
| RESEARCH → STRATEGY | Пользователь подтвердил находки |
| STRATEGY → EXECUTION | Стратегия прошла STRATEGY CRITIC (PASS) |
| EXECUTION → DEBUGGING | Обязательный цикл после каждого блока текста |
| DEBUGGING → EXECUTION | Блок не прошёл проверку (FAIL) — возврат на исправление |
| DEBUGGING → DELIVERY | Все обязательные блоки APPROVED |
| DELIVERY → REVIEW | Пользователь запрашивает правки |

### Персистентность между сессиями

Всё состояние хранится в файлах + git. Если сессия прервалась:
1. Пользователь открывает Claude Code в папке проекта
2. Claude читает `CLAUDE.md` (автоматически) → выполняет протокол запуска
3. Claude читает `projects/{name}/state.md` → определяет стейт, фазу, блок
4. Claude показывает краткий статус и спрашивает: "Всё верно? Продолжаем?"
5. При подтверждении — автоматически загружает нужные блоки и продолжает работу
6. При несогласии — корректирует state.md по указаниям пользователя

### Защита от рассинхрона state.md

Механизм валидации в начале каждой сессии:
- Claude всегда показывает текущий статус перед продолжением работы
- Пользователь подтверждает или корректирует
- Поддерживается откат: "Откатиться на {стейт}" — сброс всего после указанного стейта
- Git-история позволяет восстановить любое предыдущее состояние файлов

## STATE=STRATEGY: двойная стратегия с KB

Флоу STATE=STRATEGY состоит из 4 шагов (каждый — отдельное сообщение):

| Шаг | Что происходит |
|-----|---------------|
| **PHASE A** | Стратегия v1 в фикс-формате (Strategy Skeleton A-K). Без обращения к knowledge/ — только бриф + RESEARCH |
| **KB GATE** | `search_knowledge()` по категориям `formulas` + `examples`. Показать находки пользователю |
| **PHASE B** | Стратегия v2 на основе KB. Отметить, что изменилось и почему. Вопрос: «Стратегия 1 или 2?» |
| **STRATEGY CRITIC** | Проверка выбранной стратегии по 7 вопросам (блок 09, секция 6.3). Все 7 = YES → EXECUTION, иначе FAIL → исправить. Включает Proof Plan (F1–F4), External Research Plan, калибровку по нише/цене |

Реализация: `blocks/02_state_machine.md` (STATE=STRATEGY) + `blocks/09_debugging.md` (STRATEGY_CRITIC_V1).

## Критерии качества: техническая реализация

Двухуровневая система: формальные метрики (автоматические) + смысловой Critic Mode.

### Уровень 1: Автоматические проверки (в CLAUDE.md)

Claude выполняет перед переходом к следующему стейту:

```
Для каждого сгенерированного блока проверь:
1. Средняя длина предложения ≤ 15 слов. Если больше — перепиши.
2. Доля предложений с "вы/ваш/вам" ≥ 30%. Если меньше — добавь.
3. Стоп-лист: [уникальный, инновационный, лучший на рынке, ...]. 0 совпадений.
4. Нет абзацев длиннее 4 строк. Если есть — разбей.
5. Минимум 1 конкретная цифра/факт/срок на блок.
```

### Уровень 2: Critic Mode (26 пунктов)

Запускается автоматически в STATE=DEBUGGING после каждого блока. Реализован в `blocks/09_debugging.md`. Все 26 вопросов должны быть "Да" (Q11–12 допускают объективные исключения).

| Группа | Вопросы | Что проверяет |
|--------|---------|---------------|
| Базовые | #1–13 | JTBD, UMP/UMR, лид, Big Idea, Value Stack, гарантия, язык, срочность, логика, RESEARCH, KB, жаргон |
| Brief + Pain | #14–17 | Парадоксальный вопрос, DRE Depth (4 слоя), заслуженное решение, Pain Budget |
| Story | #18–21 | Stakes Checklist (4+/6), Emotion Layer, Inception Steps, Trust Account (5/3/2) |
| Proof | #22–26 | Diversity (3+ типа), Escalation, Specificity, Price Calibration, Mechanism-Research |

Полный список вопросов: `blocks/09_debugging.md`, секция 6.1 CRITIC_MODE_V1.

### Launch Checklist (перед DELIVERY)

Все 19 вопросов должны быть "Да". Если хоть один "Нет" — доработать:

| Группа | Вопросы | Что проверяет |
|--------|---------|---------------|
| Базовые | #1–10 | JTBD, Шварц, UMP/UMR, Big Idea, оффер, Value Stack, гарантия, срочность, язык |
| Story + Pain | #11–15 | FAQ, DRE Depth, Pain Budget, Stakes, Trust Account |
| Proof | #16–19 | Diversity, Placement (до CTA), Specificity, Mechanism-Research |

Полный список вопросов: `blocks/09_debugging.md`, секция 6.2 LAUNCH_CHECKLIST_V1.

### Ручные проверки

Claude спрашивает у пользователя:
- "Текст звучит естественно?"
- "Есть фактические ошибки?"
- "Соответствует тональности, которую мы выбрали?"

### Обработка тупиков (Deadlock Recovery)

Протокол "аварийных выходов" для ситуаций, когда процесс застревает.

#### Critic Mode FAIL 3+ раза на один блок

Счётчик попыток ведётся в `state.md`. После 3-го FAIL:
1. **СТОП** — Claude не пытается исправить снова
2. Показывает сводку: "Блок {название} не прошёл проверку 3 раза. Причины: {список}"
3. Предлагает варианты:
   - A) Вернуться к STRATEGY и изменить подход/угол
   - B) Упростить блок (убрать амбициозные элементы)
   - C) Пропустить блок и вернуться к нему позже
   - D) Принять текущую версию как есть (пользователь берёт ответственность)

#### Пользователь не может сформулировать правки

Если пользователь 2 раза ответил "не нравится" без конкретики:
1. Claude предлагает 3 конкретных варианта того, что может не нравиться (тон, структура, длина, аргументы и т.д.)
2. Показывает 2 альтернативных версии фрагмента (разные углы/тональности)
3. Спрашивает: "Какой ближе к тому, что вы хотите?"

#### Ресерч не дал результатов

Если RESEARCH не нашёл полезных данных:
1. Фиксирует: "Ресерч завершён. Данные: {что нашли}. Пробелы: {чего не хватает}"
2. Предлагает варианты:
   - A) Пользователь предоставит данные вручную
   - B) Работаем с тем, что есть (гипотезы помечены как [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ])
   - C) Сузить тему / изменить сегмент
3. Не блокирует процесс — всегда предлагает путь вперёд

## Версионность: техническая реализация (Git)

Папка `versions/` **не используется**. Версионность обеспечивается через git — это даёт полную историю изменений бесплатно.

### Конвенция коммитов

Формат: `{тип}({проект}): {описание}`

| Тип | Когда |
|-----|-------|
| `project` | Создание/настройка проекта |
| `brief` | Изменения брифа |
| `research` | Результаты ресерча |
| `strategy` | Стратегия |
| `draft` | Блоки текста (lead, story, mechanism, etc.) |
| `fix` | Исправления после DEBUGGING |
| `final` | Финальная сборка |
| `results` | Данные о результатах |

### Когда коммитить

- После каждого перехода между стейтами
- После каждого утверждённого блока (APPROVED)
- После каждого исправления (FAIL → FIX)
- При сборке финала (DELIVERY)
- При добавлении результатов

### Возврат к варианту

Пользователь: "Верни предыдущий вариант лида"
Claude:
```bash
git log --oneline -- projects/{name}/draft.md    # найти коммит
git show {commit}:projects/{name}/draft.md       # показать версию
```

### Обратная связь: results.md

После DELIVERY и публикации текста пользователь записывает результаты в `projects/{name}/results.md`:
- Метрики (конверсия, CTR, ROI)
- Результаты A/B тестов
- Обратная связь клиента
- Выводы для будущих проектов

При старте нового проекта в той же нише Claude читает `results.md` предыдущих проектов для обучения.

## Мульти-формат: техническая реализация

Помимо лендингов, система поддерживает дополнительные форматы. Шаблоны описаны в `blocks/08_asset_library.md`. Все форматы используют ту же стейт-машину и RMBC-скелет, но адаптируют структуру блоков.

| Формат | Описание | Особенности реализации |
|--------|----------|----------------------|
| **Лендинг** | Основной формат. Полный RMBC-проход | Блоки 02 + 07 |
| **Email-цепочки** | 5 писем: Разогрев → Боль → Механизм → Продукт+Оффер → Close | По 400 слов, каждое письмо = один тип лида. Блоки 02 + 08 |
| **Ads (Креативы)** | 50–150 слов. Заголовок + подзаголовок + текст + CTA | Шаблоны по платформам (VK, FB, Яндекс.Директ, Telegram). Блоки 02 + 08 |
| **VSL** | 15-минутный видеоскрипт с таймингами | Лид (0–1:30) → История+UMP → UMR → Продукт → Оффер → Close. Блоки 02 + 08 |
| **Chatbot** | 7-шаговый диалог | Хук → 3 вопроса → Мини-диагноз (UMP→UMR) → Персональный оффер → Close. Блоки 02 + 08 |

При выборе формата Claude загружает `blocks/08_asset_library.md` вместо или вместе с `blocks/07_copywriting_kernel.md`.

## Работа с несколькими сегментами: техническая реализация

На практике мульти-сегмент реализуется через отдельные проекты (версии):

```
projects/
  nutriciologia/           ← основной сегмент (v1)
  nutriciologia-v2/        ← адаптация для другого сегмента
```

При адаптации Claude:
1. Читает `final.md` основного проекта + его `results.md` (для обучения)
2. Создаёт новый проект со своим брифом (свой JTBD Map)
3. Определяет какие блоки нужно переписать (лид, история, возражения — зависят от сегмента)
4. Проходит стандартную стейт-машину (STRATEGY → EXECUTION → DEBUGGING → DELIVERY)
