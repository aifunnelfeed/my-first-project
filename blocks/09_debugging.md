12. Учтены ли формулы/примеры из knowledge/ при создании блока? Если knowledge/ не был консультирован — зафиксировать причину (MCP недоступен / пользователь отказался / нет релевантных файлов).
13. Jargon-check: все ли термины понятны целевой аудитории без гугления? Проверь каждый специализированный термин — если ЦА не использует это слово в своей повседневной речи, замени на простой аналог или добавь пояснение.
14. Brief содержит Парадоксальный вопрос и Метафору (элементы Georgi Brief Template из секции 4.1)?

17. **Pain Budget:** Секция боли (Lead + Lead Часть 2) ≥ секции механизма (Mechanism) по объёму? (см. PAIN BUDGET в секции 4.1)
18. **Story Stakes:** Есть ли ставки в истории — что герой поставил на кон? Пройден ли Stakes Checklist (4.5b) минимум на 4 из 6? Если история без ставок — она не зацепит.
19. **Story Emotion Layer:** Есть ли эмоциональный слой в каждом акте (4.5a)? Показаны ли эмоции через действия и сенсорные детали, а не через прямое называние («я испугался» → FAIL)?
20. **Inception:** Если текст содержит Big Idea или ключевой Mechanism — использован ли протокол Inception Steps (4.5c)? Есть ли information gap между загадкой и раскрытием (минимум 3 абзаца)?
21. **Trust Account:** Посчитай Trust Balance (4.5e) для каждого блока. Перед каждым CTA — минимум 5/3/2 trust deposits (для CTA #1/#2/#3). Нет ли Trust Killers (преувеличений без доказательств, фальшивой срочности, идеальных историй)?
22. **Proof Diversity:** Используются ли минимум 3 разных типа proof (по таксономии 4.11a PROOF_TAXONOMY)? Перечисли найденные типы. Если менее 3 — FAIL.
23. **Proof Escalation:** Выстроены ли доказательства по нарастающей (малый → средний → крупный результат)? Нет ли сильнейшего proof-элемента в начале (а не в Close/P.S.)? Если нарастания нет — FAIL.
24. **Proof Specificity:** Каждый proof-элемент содержит конкретику (имя, число, дата, источник)? Проверь каждый элемент — если хоть один абстрактный ("многие довольны") без конкретики — отметь.
25. **Proof-Price Calibration:** Количество proof-элементов соответствует ценовому диапазону продукта (4.11c PROOF_SELECTOR)? $7–49 → 7–15, $50–299 → 10–20, $300–999 → 15–25, $1 000+ → 25–40+. Если значительно ниже нормы — FAIL.
26. **Mechanism-Research Validation:** Содержит ли Mechanism (4.6) хотя бы 1 внешнее исследование / инсайдерский факт, подкрепляющий UMR (по [PROOF_RESEARCH_V1], 4.11b-ext)? Если Sophistication ≥ 3 — есть ли Mechanism-Proof Fusion элемент (одновременно объясняет КАК + доказывает ЧТО)? Если ниша Health/Finance и нет внешнего research — FAIL.
27. **Authority Weaving:** Если в тексте упоминается эксперт — credentials вплетены в нарратив (а не приклеены как отдельный блок «Об авторе»)? Используется паттерн, подходящий для данного Awareness/Sophistication (по матрице 4.5f [AUTHORITY_WEAVING_V1])? Credentials появляются минимум в 2 точках текста? Каждый credential привязан к окружающему контексту? Если credentials стоят одним списком или не привязаны к контексту → FAIL. Если эксперта нет в тексте → Н/П.
28. **Pain Density:** Проверь каждый абзац pain section (Lead + Lead Часть 2). Каждый абзац вносит новый ракурс (новый слой DRE / новая ситуация / новая цифра / новый голос / новое следствие)? Есть ли micro-relief каждые 3-4 абзаца (момент эмпатии/нормализации) при 5+ абзацах боли? Если 2+ абзаца подряд перефразируют одну мысль без нового ракурса → FAIL. Если 5+ абзацев боли без ни одного micro-relief → FAIL. Если блок не содержит pain section → Н/П.
29. **Placeholder Audit:** Содержит ли блок плейсхолдеры `[ВСТАВИТЬ:...]`? Если да — перечисли каждый с типом и описанием. Проверь: (a) каждый плейсхолдер стоит в логичном месте (есть нарративный контекст до и после), (b) описание достаточно конкретное для пользователя (не "нужен кейс" а "нужен кейс клиента с ростом конверсии в цифрах"), (c) нет дублирования proof-элементов с другими блоками (сверься с Proof Usage Registry в state.md).
30. **Desire Depth:** Если в тексте есть Result Projection (4.6b) или Dream State (шаг 16 в Close) — проработаны ли минимум 3 из 4 слоёв DES Depth (конкретный результат → ценность для жизни → эмоциональная награда → обновление идентичности)? Каждый результат логически вытекает из UMR? Нет ли абстрактных обещаний без конкретики («жизнь станет лучше»)? Нет ли зеркального реверса боли вместо самостоятельной desire-картинки («больше не будете мучиться» ≠ desire)? Если блок не содержит desire/result section → Н/П.
31. **Guarantee-Offer Alignment (Hormozi):** Гарантия соответствует типу из стратегии (F5)? Формулировка конкретная (не «мы гарантируем качество», а конкретное условие + действие)? Тип гарантии адекватен аудитории (Anti-guarantee для mass market = FAIL; Unconditional для premium без Reason Why = WARNING)? Если F5 не заполнена в стратегии → WARNING (рекомендовать заполнение). Если блок не содержит guarantee section → Н/П.
32. **Offer Stack Quality (Hormozi):** Если блок содержит оффер/close — пройден ли [OFFER_FUNCTIONAL_TEST_V1] (4.8c)? Каждый компонент Value Stack решает конкретную проблему из research? Названия компонентов продают (не generic «Бонус 1»)? Dream Outcome показан ДО списка компонентов («Sell the Vacation»)? Reason Why для цены присутствует? Разрыв ценность/цена ≥ 3x? Если блок не содержит offer/close section → Н/П.

Если на любой вопрос «нет» — переписать блок. Для вопросов 11–12: если данные не использованы по объективной причине (пользователь решил пропустить), зафиксировать это и продолжить. Для вопроса 13: ориентируйся на профиль ЦА из брифа (образование, уровень экспертизы в теме). Для вопроса 27: если в тексте нет эксперта и strategy.md секция L = «Эксперт: отсутствует» → Н/П. Для вопроса 28: если блок не содержит pain section (например, Close, FAQ, Proof) → Н/П. Для вопроса 29: плейсхолдеры НЕ влияют на PASS/FAIL — они фиксируются как INFO в отчёте и подсчитываются отдельно. Для вопроса 30: если блок не содержит desire/result section (Lead, Pain Deep Dive, Bridge, FAQ, Proof) → Н/П.
Для вопроса 31: если блок не содержит guarantee/offer section → Н/П. Если F5 не заполнена в стратегии — WARNING, не FAIL.
Для вопроса 32: если блок не содержит offer/close section → Н/П. Оценивается совместно с Q31 (guarantee + offer = целостная проверка по Хормози).

### 6.3. STRATEGY CRITIC (проверка стратегии)
КОД ДОСТУПА: [STRATEGY_CRITIC_V1]

**TRIGGER:** После выбора пользователем стратегии (v1 или v2) в STATE=STRATEGY.

**ЧЕК-ЛИСТ (9 ВОПРОСОВ):**
После выбора стратегии — проверь (да/нет + исправление):

1. Awareness level подтверждён данными из RESEARCH (не угадан)?
2. Sophistication level соответствует реальному состоянию рынка?
3. УМ Проблемы (UMP) объясняет, почему прошлые решения не работали?
4. УМ Решения (UMR) имеет название, механику и отличие от конкурентов?
5. Proof Plan (по формату 4.11) содержит минимум 3 доказательства с указанием типов (по PROOF_TAXONOMY), источников и планируемого размещения (Lead/Mechanism/Offer/Close)? Соответствует ли нише и ценовому диапазону (по PROOF_SELECTOR)? Если Sophistication ≥ 3 или ниша Health/Finance — включён ли External Research Plan (F4)?
6. Core Promise — конкретная (с цифрой/сроком/результатом), не абстрактная?
7. Стратегия не противоречит данным из Evidence Map (нет утверждений без источника)?
8. **Value Equation (Hormozi):** Все 4 переменные заполнены (D2)? Dream Outcome конкретен (сцена, не абстракция)? Speed to Value (D3) — Quick Win реалистичен (не пустое обещание)? Guarantee Strategy (F5) — тип выбран и обоснован?
9. **Target Segments (M):** Определены ли 3 сегмента (Primary, Secondary, Acceptable Loss)? Описания конкретные (не "все заинтересованные")? Есть обоснование категоризации? Если M не заполнена → FAIL с рекомендацией заполнить.
10. **Core Emotion (N):** Выбрана ли одна ключевая эмоция из 10? Обоснование связано с ЦА и Awareness/Sophistication? Если N не заполнена → FAIL с рекомендацией заполнить.

Если на любой вопрос «нет» — исправить стратегию и повторить проверку.
PASS → сохранить в strategy.md, переход к EXECUTION.
FAIL → показать причины, исправить, повторить.
