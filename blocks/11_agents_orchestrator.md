# БЛОК 11: ОРКЕСТРАТОР СУБАГЕНТОВ (Agent Orchestration + Dispatch + Prompt Templates)

## РАЗДЕЛ 7: ОРКЕСТРАТОР СУБАГЕНТОВ (AGENT ORCHESTRATOR)

### 7.1. ОБЩИЕ ПРАВИЛА СУБАГЕНТОВ
КОД ДОСТУПА: [SUBAGENT_RULES_V1]

**8 правил для ВСЕХ субагентов:**

1. **Нет доступа к blocks/.** Субагенты НЕ читают блоки автоматически — все инструкции передаются в промпте.
2. **Контекст проекта: 3-5 предложений.** Из brief.md/strategy.md — только самое важное, НЕ весь файл.
3. **Строгий формат вывода.** Каждый субагент возвращает ответ ТОЧНО по шаблону из своей секции. Отклонение от формата = невалидный результат.
4. **Обработка ошибок.** Если инструмент (WebSearch/MCP) недоступен → субагент возвращает `STATUS: TOOL_UNAVAILABLE` + описание того, что не смог сделать + частичные результаты (если есть).
5. **Запрет на выдумку.** Запрещено придумывать факты, цифры, цитаты, источники. Если данные не найдены → `НЕ НАЙДЕНО`.
6. **Инструмент запуска.** Claude Code Agent tool (`subagent_type="general-purpose"`). Субагенты запускаются параллельно, когда задачи независимы.
7. **Результаты показываются пользователю ПЕРЕД интеграцией** в файлы проекта (правило из CLAUDE.md). Молчаливая вставка запрещена.
8. **Язык.** Субагент работает на языке проекта (обычно RU для русскоязычных проектов, EN для англоязычных запросов).

### 7.3. ПРАВИЛА ДИСПАТЧА
КОД ДОСТУПА: [DISPATCH_RULES_V1]

**STATE=RESEARCH (полный ресерч):**
- Если WebSearch доступен → dispatch A + B + C параллельно
- Пока субагенты работают → главный агент выполняет JTBD_DECODER + SCHWARTZ_MATRIX
- По возвращении → собрать в research_raw.md → DOUBLE FILTER (7.11)
- Если нужен PROOF_RESEARCH → dispatch D (обычно позже, внутри EXECUTION)

**STATE=EXECUTION (PHASE C):**
- Data gap типа B (нужен WebSearch) → dispatch E (Research-Mini)
- PROOF_MINING шаг 5 (пробелы Scientific/Historical/Authority) → dispatch D (Proof Research)

**STATE=DEBUGGING (после каждого блока COPY) — ОБЯЗАТЕЛЬНО:**
- Dispatch F (Block Critic) с текстом блока + контекст проекта
- Получить CRITIC REPORT → показать пользователю
- PASS → "Принять блок?"
- FAIL → показать CORRECTIONS → "Применить исправления?"

**STATE=DELIVERY (перед FINAL SELF-CHECK):**
- После сборки final.md → dispatch G (Launch Critic)
- PASS → переход к FINAL SELF-CHECK
- FAIL → показать LAUNCH REPORT → исправить → перезапустить G

**FALLBACK (всегда):**
Если Agent tool недоступен → выполнять проверки in-context (блок 09):
- F → 26 вопросов CRITIC_MODE_V1 (секция 6.1)
- G → 19 вопросов LAUNCH_CHECKLIST_V1 (секция 6.2)
- A-E → серийный ресерч в основном агенте

   - Solution Aware (3): Mechanism Lead (почему ЭТО решение лучше)
   - Product Aware (4): Offer Lead (deal, бонусы, гарантия)
   - Most Aware (5): Direct Lead (цена, оффер, CTA в первых строках)
5. **Big Idea:** Есть ли Big Idea? Обязательна при Sophistication >= 3.
6. **Value Stack:** Есть ли Value Stack с конкретными цифрами (стоимость каждого элемента)?
7. **Guarantee:** Гарантия снимает главный риск (барьер: {барьер #1})?
8. **Language:** Язык живой, разговорный, без корпоративного жаргона?
9. **Urgency:** Есть ли 2+ триггера срочности (дедлайн, лимит, повышение цены, сезонность)?
10. **Flow:** Каждое предложение логически ведёт к следующему? Нет ли "провалов" в аргументации?
11. **Research Usage:** Использованы ли данные из RESEARCH (JTBD map, VOC-фразы, DRE/DES, барьеры)? Сравни текст с VOC-фразами выше — есть ли пересечения? Если RESEARCH пропущен — помечены ли гипотезы как [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ]?
12. **KB Usage:** Учтены ли формулы/примеры из knowledge base при создании блока? Если нет — зафиксировать причину (MCP недоступен / пользователь отказался / нет релевантных файлов).
13. **Jargon Check:** Все ли специализированные термины понятны ЦА ({ЦА}) без гугления? Проверь каждый термин — если ЦА не использует его в повседневной речи, он должен быть заменён или пояснён.

ГРУППА 2: BRIEF + PAIN (14-17)

14. **Brief Elements:** Есть ли в тексте Парадоксальный вопрос и Метафора (элементы Georgi Brief Template)?
15. **Pain Depth (DRE 4 слоя):** Проработаны ли все 4 слоя глубины боли:
    - Слой 1 (Поверхность): видимая проблема — что конкретно не работает
    - Слой 2 (Цена): деньги, время, упущенные возможности
    - Слой 3 (Эмоция): фрустрация, стыд, бессилие, злость
    - Слой 4 (Идентичность): что проблема говорит обо мне как о человеке/профессионале
    Если слои 3-4 отсутствуют или формальные → FAIL.
16. **Earned Solution:** Хочет ли читатель узнать решение К МОМЕНТУ, когда оно предлагается? Тест: если убрать механизм и оффер — будет ли читатель разочарован? Если нет → Pain Amplification слишком слабая.
17. **Pain Budget:** Секция боли (Lead + Pain Amplification) >= секции механизма (Bridge + Mechanism) по объёму?
    - Sophistication 1-2: соотношение боль:механизм >= 1:1
    - Sophistication 3-4: >= 1.5:1
    - Sophistication 5: допустимо 0.5:1

ГРУППА 3: STORY + TRUST (18-21)

18. **Story Stakes:** Есть ли ставки в истории — что герой поставил на кон? Stakes Checklist (6 пунктов):
    (1) Личная инвестиция (деньги/репутация/отношения на кону)
    (2) Relatable moment (читатель сам переживал подобное)
    (3) Irreversible (нельзя вернуться назад — мосты сожжены)
    (4) Inevitable (результат логичен, а не "повезло")
    (5) Intimate (деталь, которую "стыдно" рассказывать)
    (6) "Почему мне не всё равно?" (связь с проблемой читателя)
    МИНИМУМ: 4 из 6 = PASS. Менее 4 → FAIL.
19. **Story Emotion Layer:** Показаны ли эмоции через действия и сенсорные детали, а НЕ через прямое называние?
    FAIL: «я испугался», «мне стало грустно»
    PASS: «руки дрожали, я не мог набрать номер», «горло сдавило, слова застряли»
20. **Inception:** Если текст содержит Big Idea или ключевой Mechanism — использован ли Inception Steps?
    (1) Загадка — упоминание результата/объекта без объяснения
    (2) Хлебные крошки — частичные подсказки по ходу текста
    (3) Ложный пик — кажется, вот-вот раскроется, но поворот
    (4) Раскрытие — идея как вывод, который читатель "сам сделал"
    Между загадкой и раскрытием — минимум 3 абзаца. Если меньше → FAIL.
21. **Trust Account:** Посчитай Trust Balance для текста.
    Trust Deposits (позитивные): Specificity (конкретика), Vulnerability (уязвимость автора), Prediction (точный прогноз), Proof (доказательство), Ethical Gate (честное предупреждение), Contrarian Honesty (признание недостатков), Third-party Validation (сторонняя валидация), Consistency (последовательность)
    Trust Killers (негативные): Преувеличение без доказательств, Идеальная история без провалов, Фальшивая срочность, Противоречия в тексте, Манипулятивный тон, Отсутствие доказательств, Корпоративный язык, Скрытые условия
    Баланс >= 3 на блок = PASS, 1-2 = WARN, <= 0 = FAIL
    Перед CTA #1: минимум 5 trust deposits
    Перед CTA #2: ещё 3+ deposits
    Перед CTA #3: финальные 2+ deposits

ГРУППА 4: PROOF (22-26)

22. **Proof Diversity:** Используются ли минимум 3 разных типа proof? 10 типов (таксономия):

    (4) Media Mention (5) Scientific Study (6) Track Record
    (7) Historical Data (8) Personal Experience (9) Scripture/Sacred Text
    (10) Documentary Proof (патенты, налоговые формы, гос.документы)

23. **Proof Escalation:** Доказательства по нарастающей (малый → средний → крупный результат)? Сильнейший proof НЕ в начале (а в Close/P.S.)? Если нарастания нет → FAIL.
24. **Proof Specificity:** Каждый proof-элемент содержит конкретику (имя, число, дата, источник)? Если хоть один абстрактный ("многие довольны" без конкретики) → отметить.
25. **Proof-Price Calibration:** Количество proof-элементов соответствует ценовому диапазону ({цена}):
    $7-49 → 7-15 элементов
    $50-299 → 10-20 элементов
    $300-999 → 15-25 элементов
    $1 000+ → 25-40+ элементов
    Корректировки: Sophistication >= 3 → +5 элементов. Ниша Health/Finance → +5 элементов.
    Если значительно ниже нормы → FAIL.
26. **Mechanism-Research Validation:** Содержит ли Mechanism хотя бы 1 внешнее исследование / инсайдерский факт, подкрепляющий UMR? Если Sophistication >= 3 — есть ли Mechanism-Proof Fusion (одновременно объясняет КАК + доказывает ЧТО)? Если ниша Health/Finance и нет внешнего research → FAIL.
