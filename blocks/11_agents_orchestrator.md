## РАЗДЕЛ 7: ОРКЕСТРАТОР СУБАГЕНТОВ (AGENT ORCHESTRATOR)

### 7.1. ОБЩИЕ ПРАВИЛА СУБАГЕНТОВ
КОД ДОСТУПА: [SUBAGENT_RULES_V1]

**8 правил для ВСЕХ субагентов:**

1. **Нет доступа к blocks/.** Субагенты НЕ читают блоки автоматически — все инструкции передаются в промпте.
2. **Контекст проекта: 3-5 предложений.** Из brief.md/strategy.md — только самое важное, НЕ весь файл.
3. **Строгий формат вывода.** Каждый субагент возвращает ответ ТОЧНО по шаблону из своей секции. Отклонение от формата = невалидный результат.
4. **Обработка ошибок.** Если инструмент (WebSearch/MCP) недоступен → субагент возвращает `STATUS: TOOL_UNAVAILABLE` + описание того, что не смог сделать + частичные результаты (если есть).
5. **Запрет на выдумку.** Запрещено придумывать факты, цифры, цитаты, источники. Если данные не найдены → `НЕ НАЙДЕНО`.
6. **Инструмент запуска.** Claude Code Agent tool (`subagent_type="general-purpose"`). Субагенты запускаются параллельно, когда задачи независимы.
7. **Результаты показываются пользователю ПЕРЕД интеграцией** в файлы проекта (правило из CLAUDE.md). Молчаливая вставка запрещена.
8. **Язык.** Субагент работает на языке проекта (обычно RU для русскоязычных проектов, EN для англоязычных запросов).

### 7.3. ПРАВИЛА ДИСПАТЧА
КОД ДОСТУПА: [DISPATCH_RULES_V1]

**STATE=RESEARCH (полный ресерч):**
- Если WebSearch доступен → dispatch A + B + C параллельно
- Пока субагенты работают → главный агент выполняет JTBD_DECODER + SCHWARTZ_MATRIX
- По возвращении A+B+C → dispatch H (Research Assembler) с выходами A+B+C → секция 7.12
- H возвращает готовый research_raw.md → DOUBLE FILTER (7.11)
- Если нужен PROOF_RESEARCH → dispatch D (обычно позже, внутри EXECUTION)

**STATE=EXECUTION (PHASE C):**
- Data gap типа B (нужен WebSearch) → dispatch E (Research-Mini)
- PROOF_MINING шаг 5 (пробелы Scientific/Historical/Authority) → dispatch D (Proof Research)

**STATE=EXECUTION (PHASE C — KB-SCOUT, усиление KNOWLEDGE GATE):**
- Перед каждым блоком COPY (кроме Proof) → dispatch I (KB-Scout) ПАРАЛЛЕЛЬНО с подготовкой контекста блока → блок 11, секция 7.13 [SUBAGENT_I_KBSCOUT_V1]
- ИСКЛЮЧЕНИЕ: block_type = Proof → НЕ dispatch I (Proof использует собственный PROOF_MINING_V1, блок 07, секция 4.9b)
- Скаут НЕ заменяет собственный поиск основного агента — он **усиливает** его дополнительным материалом
- По возвращении I → показать KB-SCOUT REPORT пользователю → основной агент объединяет свои находки + REPORT скаута → пишет блок
- Fallback (Agent tool или MCP скауту недоступен): основной агент работает через KNOWLEDGE GATE самостоятельно (search_knowledge / чтение файлов)

**STATE=DEBUGGING (после каждого блока COPY) — ОБЯЗАТЕЛЬНО:**

- Получить CRITIC REPORT → показать пользователю
- PASS → "Принять блок?"
- FAIL → показать CORRECTIONS → "Применить исправления?"

**Шаг 1 — LAUNCH CRITIC (обязательно):**
- После сборки final.md → dispatch G (Launch Critic)
- PASS → переход к Шагу 2
- FAIL → показать LAUNCH REPORT → исправить → перезапустить G

**Шаг 2 — AUDIENCE SIMULATION (обязательно):**

- CRITICAL_FIX → обязательные правки → повторная симуляция (макс. 2 итерации)

**STATE=STRATEGY (Alternatives Scout — ФОНОВЫЙ):**
- После генерации PHASE A (стратегия v1) → dispatch J В ФОНЕ (run_in_background=true)
- J работает ПАРАЛЛЕЛЬНО с KB GATE и PHASE B — НЕ блокирует основной поток
- Контекст для J: brief-context (3-5 предложений) + research-context (JTBD, DRE/DES, VOC топ-5, UMP/UMR из стратегии v1) + strategy v1 (секции A-K)
- По возвращении J: главный агент сохраняет ALTERNATIVES REPORT в alternatives.md, показывает пользователю КРАТКУЮ СВОДКУ (1-2 строки на категорию) ПОСЛЕ завершения STRATEGY (не прерывая текущий поток)
- Если J вернулся ДО завершения STRATEGY GATE → показать результаты J вместе с финальным вопросом ("Стратегия 1 или 2?"), добавив: "Также есть альтернативные идеи — см. alternatives.md или скажите 'Покажи альтернативы'"
- Если J вернулся ПОСЛЕ STRATEGY GATE → показать при следующем сообщении
- Fallback (Agent tool недоступен): пропустить автодиспатч. Альтернативы доступны только через ручную команду (in-context генерация главным агентом)

**РУЧНОЙ ДИСПАТЧ — команда "Альтернативы" / "Alternatives" (любой стейт):**
- Пользователь вводит "Альтернативы" (или "Alternatives", "Альтернативы для {блок}") → dispatch J
- Контекст адаптируется по текущему стейту:

  | Стейт | Что передать J |
  |-------|---------------|
  | INPUT/QUERY | brief-context only |
  | RESEARCH | brief-context + research (сырой или финальный) |
  | STRATEGY | brief + research + strategy (v1 и/или v2) |
  | EXECUTION | brief + research + strategy + текущий draft.md + текущий block_type |
  | DEBUGGING | brief + research + strategy + текущий блок + CRITIC REPORT (FAIL corrections) |
  | DELIVERY/REVIEW | brief + research + strategy + final.md |

- Ручной вызов = НЕ фоновый. Результат показывается пользователю сразу
- Если пользователь уточнил блок ("Альтернативы для заголовков") → J фокусируется на одной категории

**FALLBACK (всегда):**
Если Agent tool недоступен → выполнять проверки in-context (блок 09):
- F → 28 вопросов CRITIC_MODE_V1 (секция 6.1)
- G → 21 вопрос LAUNCH_CHECKLIST_V1 (секция 6.2)
- H → главный агент собирает research_raw.md вручную (текущее поведение)
- A-E → серийный ресерч в основном агенте
- I → основной агент выполняет KNOWLEDGE GATE самостоятельно (search_knowledge / чтение файлов — текущее поведение)
- J → главный агент генерирует альтернативы in-context (сокращённый набор: 1 Big Idea + 2 Headlines + 1 Enhancement)

- In medias res: начни с середины истории

КАТЕГОРИЯ 5: ENHANCEMENTS (креативные усиления текущего направления)

- Скрытый бонус / Easter egg в тексте
- Pattern interrupt (что-то, что ломает привычный ритм sales page)

КАТЕГОРИЯ 6: CREATIVE HOOKS (дикие идеи — без цензуры)

МОДЕЛЬ РЕШЕНИЙ — ИНСТРУКЦИЯ
==============================

{подставляется одна из четырёх моделей:}

[ANALYST]: Ты принимаешь решения через анализ данных. Ищешь цифры, исследования, конкретику. Расплывчатые обещания раздражают. "Покажите мне доказательства." Сравниваешь с альтернативами. Читаешь медленно, обращаешь внимание на мелкий шрифт. Если proof слабый — уходишь.

[SOCIAL]: Ты принимаешь решения через мнение других. Ищешь отзывы, кейсы, "кто ещё это купил". Имена и истории реальных людей — твой главный триггер. "Если им помогло — может, и мне поможет." Без social proof чувствуешь себя одиноким в решении.

[IMPULSIVE]: Ты принимаешь решения быстро, на эмоции. Яркий заголовок + сильное обещание + понятный CTA = покупка. Длинные объяснения утомляют. Если не зацепило в первые 30 секунд — закрываешь. Скидка/дедлайн/бонус — работают моментально.

[METHODICAL]: Ты принимаешь решения пошагово. Тебе нужно понять ПРОЦЕСС: что буду делать на 1-й неделе, на 2-й, какой результат на каждом этапе. Абстрактные обещания без структуры вызывают недоверие. "Как именно это работает?" — твой главный вопрос.

#### 7.16.1. ШАГ 1: ГЕНЕРАЦИЯ ПЕРСОН (выполняет главный агент)

**Источники данных:**
- research.md: JTBD, VOC-цитаты, DRE/DES, возражения
- strategy.md: секция A (Audience Snapshot), секция M (Target Segments), секция C (Sophistication)
- brief.md: продукт, ЦА, цена

**Правила генерации:**

1. **Количество:** 5-8 персон. По умолчанию 6 (2 Primary + 2 Secondary + 1 Acceptable Loss + 1 BURNED).
2. **Покрытие decision models:** минимум по 1 персоне на каждую модель (ANALYST, SOCIAL, IMPULSIVE, METHODICAL). Оставшиеся — по усмотрению, но разнообразие приоритетнее.
3. **Обязательный BURNED-читатель:** Одна персона ВСЕГДА имеет скептицизм = BURNED (был обманут ранее в этой нише). Назначать из Primary или Secondary — НЕ из Acceptable Loss.
4. **Сегменты из strategy.md (M):**
   - Primary (минимум 2 персоны) — ДОЛЖЕН удержать и конвертировать
   - Secondary (минимум 1 персона) — хотим удержать, но не ценой ослабления для Primary
   - Acceptable Loss (максимум 1 персона) — осознанно теряем
5. **Реализм:** Каждая персона строится на данных из research.md. "Боль" — из VOC. "Опыт" — из возражений. "Контекст" — из JTBD.
6. **Разнообразие:** Персоны отличаются по: возрасту, опыту, скептицизму, модели решений, стоп-факторам.

#### 7.16.5. ШАГ 5: РЕШЕНИЕ И ДЕЙСТВИЕ

**По вердикту SIMULATION REPORT:**

- **NEEDS_FIX:** Показать отчёт + рекомендации → "Есть необязательные исправления. Исправить или принять как есть?"

  - Принять → FINAL SELF-CHECK с пометкой `SIMULATION_OVERRIDE: {описание}` в state.md
- **CRITICAL_FIX:** Показать отчёт → "Текст не удерживает Primary. Обязательные исправления:" → применить → перезапустить ПОЛНУЮ симуляцию
