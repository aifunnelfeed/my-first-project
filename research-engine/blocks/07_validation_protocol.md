# БЛОК 7: ПРОТОКОЛ ВАЛИДАЦИИ (Validation Protocol)

## НАЗНАЧЕНИЕ

Кросс-валидация данных из COLLECTION и SIMULATION, финальная оценка уверенности, управление гипотезами, анализ пробелов. Последний чекпоинт перед сборкой research_pack/.

**ВХОД:** collection.md + synthesis.md + simulation_report.md (если есть)
**ВЫХОД:** validation_report.md
**ЗАГРУЗКА:** STATE=VALIDATION → блоки 01 + 02 + 07

## РАЗДЕЛ 1: КРОСС-ВАЛИДАЦИЯ

### 1.1. CROSS-VALIDATION PROTOCOL
КОД ДОСТУПА: [CROSS_VALIDATION_V1]

**ЗАДАЧА:** Сопоставить то, что COLLECTION нашёл (факты, VOC, тренды), с тем, как персоны SIMULATION отреагировали.

**3 ТИПА НАХОДОК:**

| Тип | Описание | Значение |
|-----|---------|---------|
| **CONFIRM** | Данные collection подтверждены реакцией персон | Усиливает уверенность. Факт можно использовать смело. |
| **CONTRADICT** | Данные говорят X, но персоны реагируют Y | Требует разбора. Возможно: данные устарели / сегментация / ошибка формулировки. |
| **BLIND_SPOT** | Симуляция выявила то, чего нет в collection | Новая информация. Добавить в synthesis или пометить [HYPOTHESIS]. |

**ФОРМАТ:**

```markdown
## CROSS-VALIDATION

| # | Находка | Тип | Источник (Collection) | Источник (Simulation) | Импликация | Действие |
|---|---------|-----|----------------------|----------------------|-----------|---------|
| 1 | {описание} | CONFIRM | {секция collection.md} | {персона, тест, балл} | {что это значит} | {использовать как есть / усилить / проверить} |
| 2 | {описание} | CONTRADICT | {секция} | {персона, тест} | {что это значит} | {пересмотреть / уточнить / отметить конфликт} |
| 3 | {описание} | BLIND_SPOT | — | {персона, тест} | {что это значит} | {добавить в synthesis / [HYPOTHESIS] / запросить данные} |

### Сводка
- Confirmations: {N}
- Contradictions: {N} — {критичные?}
- Blind Spots: {N} — {из них критичных: N}
```

**ВАРИАНТ ДЛЯ QUICK (без simulation):**
Кросс-валидация выполняется только на основе внутренней согласованности collection.md:
- Проверка: данные VOC ↔ конкурентный анализ ↔ тренды — нет ли противоречий
- Формат тот же, но столбец "Источник (Simulation)" заменяется на "Источник (Collection #2)"

**7 КАТЕГОРИЙ:**

| Категория | Источники | Покрытие | Базовая уверенность | Коррекция (Simulation) | Финальная |
|-----------|-----------|----------|--------------------|-----------------------|-----------|

| VOC | {перечислить} | {full/partial/missing} | {HIGH/MED/LOW} | {коррекция} | {HIGH/MED/LOW} |
| Fears / Desires | {перечислить} | {full/partial/missing} | {HIGH/MED/LOW} | {коррекция} | {HIGH/MED/LOW} |
| Competitors | {перечислить} | {full/partial/missing} | {HIGH/MED/LOW} | {коррекция} | {HIGH/MED/LOW} |
| Scene Bank | {перечислить} | {full/partial/missing} | {HIGH/MED/LOW} | {коррекция} | {HIGH/MED/LOW} |
| Decision Model | {перечислить} | {full/partial/missing} | {HIGH/MED/LOW} | {коррекция} | {HIGH/MED/LOW} |
| Trends | {перечислить} | {full/partial/missing} | {HIGH/MED/LOW} | {коррекция} | {HIGH/MED/LOW} |

**ПРАВИЛА КОРРЕКЦИИ:**
- Если ≥3 персоны CONFIRM данные категории → ↑ (повысить на 1 уровень, макс HIGH)

**ВЫВОД:**

## РАЗДЕЛ 3: РЕЕСТР ГИПОТЕЗ

### 3.1. HYPOTHESIS VALIDATION
КОД ДОСТУПА: [HYPOTHESIS_VALIDATION_V1]

**ЗАДАЧА:** Обновить статусы всех гипотез из state.md на основе данных collection + synthesis + simulation.

**4 СТАТУСА:**

| Статус | Критерий | Действие |
|--------|---------|---------|
| **CONFIRMED** | Данные + simulation согласуются | Использовать как факт в research_pack |
| **REJECTED** | Прямое противоречие в данных или simulation | Убрать из research_pack или пометить как ошибку |
| **REVISED** | Частично подтверждено, требует уточнения | Переформулировать и пометить [REVISED] |
| **OPEN** | Нет данных ни за, ни против | Оставить как [HYPOTHESIS] в research_pack |

**ФОРМАТ:**

```markdown
## Hypothesis Registry (Updated)

| # | Гипотеза | Предыдущий статус | Новый статус | Доказательство | Действие |
|---|----------|------------------|-------------|---------------|---------|
| H1 | {формулировка} | OPEN | CONFIRMED | {что подтвердило — данные + персона} | Использовать в {файл research_pack} |
| H2 | {формулировка} | OPEN | REJECTED | {что опровергло} | Убрать из synthesis |
| H3 | {формулировка} | OPEN | REVISED | {что изменилось} | Переформулировать: "{новая версия}" |
| H4 | {формулировка} | OPEN | OPEN | Нет данных | Оставить [HYPOTHESIS] |
```

**ПРАВИЛО:** REJECTED гипотезы НЕ удаляются из реестра — они остаются с пометкой. Это ценная информация ("мы думали X, но оказалось Y").

## РАЗДЕЛ 6: ЧЕКПОИНТ ПОЛЬЗОВАТЕЛЯ

### 6.1. VALIDATION CHECKPOINT
КОД ДОСТУПА: [VALIDATION_CHECKPOINT_V1]

**ПОРЯДОК:**
1. Показать validation_report.md пользователю
2. Ждать решения (A / B / C / D)
3. Выполнить выбранное действие

**БЛОКИРУЮЩЕЕ УСЛОВИЕ:**
```
⚠️ CRITICAL GAPS: {N} из 5 критичных файлов не готовы.

Переход в DELIVERY невозможен без:
A) Заполнения gaps пользователем
B) Backtrack для дополнительного сбора
C) Явного принятия рисков (вариант D)
```

**ПРАВИЛО:** Если ≥3 CRITICAL gaps → усиленное предупреждение. Вариант D доступен, но с явным disclamer: "Research pack будет содержать {N} критичных пробелов. Copycraft может не получить достаточно данных для качественного текста."

## РАЗДЕЛ 7: ПРАВИЛА

1. **Validation обязательна.** Нельзя перейти в DELIVERY без прохождения VALIDATION.
2. **Для QUICK:** кросс-валидация без simulation (только внутренняя согласованность). Confidence Scoring без коррекции.
3. **Traceability.** Каждая находка кросс-валидации ссылается на конкретные секции collection/synthesis/simulation.
4. **State.md update.** После валидации обновить: Hypothesis Registry, Data Confidence, пройденные стейты.
5. **Однократность.** Validation выполняется один раз. Если пользователь выбрал B (fill gaps) — после заполнения делается RE-VALIDATION (сокращённая: только изменённые категории).
6. **Git.** Формат коммита: `research({проект}): validation — {N}/7 HIGH confidence, {M} gaps`
