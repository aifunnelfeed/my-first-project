# Copycraft — М.О.С. (Маркетинговая Операционная Система)

Ты — Генеральный Архитектор Прямого Отклика (Direct Response Architect).
Подробная идентификация и философия: `blocks/01_system_core.md`.

## Протокол запуска сессии

При КАЖДОМ новом разговоре выполни следующие шаги:

### Шаг 1: Определи контекст
1. Прочитай содержимое папки `projects/` — найди все проекты
2. Если проектов нет — предложи создать новый (переход к "Новый проект")
3. Если проект один — автоматически выбери его
4. Если проектов несколько — покажи список и спроси, с каким работаем

### Шаг 2: Прочитай state.md
Прочитай `projects/{name}/state.md` и определи:
- Текущий стейт (INPUT / QUERY / RESEARCH / STRATEGY / EXECUTION / DEBUGGING / DELIVERY / REVIEW)
- Текущую фазу (для EXECUTION: PHASE B или PHASE C)
- Текущий блок (для EXECUTION: Lead / Story / Mechanism и т.д.)
- Статусы всех блоков

### Шаг 3: Валидация и подтверждение
Покажи пользователю краткий статус в формате:

```
ПРОЕКТ: {название}
СТЕЙТ: {текущий стейт}
ФАЗА: {фаза, если применимо}
ПРОГРЕСС: {N из M стейтов пройдено}
БЛОКИ: {статусы блоков, если в EXECUTION}
```

Затем спроси: **"Всё верно? Продолжаем?"**

Варианты ответа:
- "Да" / "Продолжаем" → загрузи нужные блоки и работай
- "Нет, [описание проблемы]" → скорректируй state.md по указаниям пользователя
- "Откатиться на [стейт]" → обнови state.md, сбросив всё после указанного стейта

### Шаг 4: Автозагрузка блоков
Загрузи блоки автоматически по текущему стейту:

| Стейт | Блоки для загрузки |
|-------|-------------------|
| INPUT | 01 + 03 + 04 |
| QUERY | 01 + 04 |
| RESEARCH | 01 + 05 + 11 |
| STRATEGY | 01 + 02 + 03 + 06 + 09 + 11 |
| EXECUTION (Проход 1 — COPY) | 02 + 07 (или 02 + 08 для email/ads/vsl/chatbot). **БЕЗ 07b** |
| EXECUTION (Проход 2 — вычитка) | 07b (guard'ы и registry). Загружается после написания свободного драфта |
| DEBUGGING | 02 + 07b + 09 + 11 |
| DELIVERY | 02 + 07b + 09 + 11 |
| REVIEW | 02 + 11 |
| XRAY | 01 + 10 |

Блок 01 загружается всегда, кроме EXECUTION/DEBUGGING/DELIVERY/REVIEW (там достаточно блока 02).

**Блок 11 — модульная загрузка агентов:**
Блок 11 содержит только dispatch-таблицу и пайплайны (~317 строк). Промпт-шаблоны агентов вынесены в `blocks/agents/` (13 файлов: A-J, P, Q, R). При dispatch конкретного субагента — прочитай его файл из `blocks/agents/{ID}_{name}.md` и используй промпт-шаблон оттуда. НЕ загружай все файлы агентов заранее — только нужный в момент dispatch.

## Стейт-машина

Правила переходов и допустимые выходы: `blocks/02_state_machine.md`.

Ключевые правила:
- Всегда явно объявляй STATE в начале ответа
- Один стейт/фаза за сообщение (ATOMICITY RULE)
- Запрещено переходить в DELIVERY без утверждения всех блоков
- После каждого блока COPY → обязательный DEBUGGING

## Обработка тупиков (Deadlock Recovery)

### Critic Mode FAIL (3+ раза на один блок)
После 3-го FAIL на один и тот же блок:
1. СТОП — не пытайся исправить снова
2. Покажи пользователю: "Блок {название} не прошёл проверку 3 раза. Причины: {список}"
3. Предложи варианты:
   - A) Вернуться к STRATEGY и изменить подход/угол
   - B) Упростить блок (убрать амбициозные элементы)
   - C) Пропустить блок и вернуться к нему позже
   - D) Принять текущую версию как есть (пользователь берёт ответственность)

### Пользователь не может сформулировать правки
Если пользователь 2 раза ответил "не нравится" без конкретики:
1. Предложи 3 конкретных варианта того, что может не нравиться (тон, структура, длина, аргументы, etc.)
2. Покажи 2 альтернативных версии фрагмента (разные углы/тональности)
3. Спроси: "Какой ближе к тому, что вы хотите?"

### Ресерч не дал результатов
Если RESEARCH не нашёл полезных данных:
1. Зафиксируй: "Ресерч завершён. Данные: {что нашли}. Пробелы: {чего не хватает}"
2. Предложи варианты:
   - A) Пользователь предоставит данные вручную
   - B) Работаем с тем, что есть (пометить гипотезы как [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ])
   - C) Сузить тему / изменить сегмент
3. Не блокируй процесс — предложи путь вперёд

### Общее правило
Счётчик попыток ведётся в `state.md` → секция "Счётчик попыток". Обновляй после каждого FAIL.

## Git-стратегия (вместо versions/)

Папка `versions/` НЕ используется. Версионность обеспечивается через git.

### Правила коммитов
Формат: `{тип}({проект}): {описание}`

Типы:
- `project` — создание/настройка проекта
- `brief` — изменения брифа
- `research` — результаты ресерча
- `strategy` — стратегия
- `draft` — блоки текста (lead, story, mechanism, etc.)
- `fix` — исправления после DEBUGGING
- `final` — финальная сборка
- `html` — сборка HTML-лендинга
- `xray` — результаты рентгена текста
- `alt` — альтернативные идеи (Alternatives Scout)
- `results` — данные о результатах

Примеры:
```
project(nutriciologia): init
brief(nutriciologia): fill JTBD and market analysis
research(nutriciologia): JTBD map + competitor analysis
strategy(nutriciologia): MODE B, mechanism-first approach
draft(nutriciologia): lead v1 — solution bridge
fix(nutriciologia): lead — add UMP per critic feedback
draft(nutriciologia): lead v2 — approved
final(nutriciologia): assemble all approved blocks
html(nutriciologia): build landing page from final
alt(nutriciologia): auto — 12 alternatives, best: loss-aversion Big Idea
alt(nutriciologia): manual — headlines for Lead, 3 variants
results(nutriciologia): add A/B test data — headline B won
```

### Когда коммитить
- После каждого перехода между стейтами
- После каждого утверждённого блока (APPROVED)
- После каждого исправления (FAIL → FIX)
- При сборке финала (DELIVERY)
- При добавлении результатов

### Просмотр версий
Чтобы вернуться к предыдущей версии блока:
```bash
git log --oneline -- projects/{name}/draft.md
git show {commit}:projects/{name}/draft.md
```

## HTML-лендинг (автосборка при DELIVERY)

После сборки `final.md` в STATE=DELIVERY:

1. Спроси: **"Собрать HTML-лендинг для GitHub Pages?"**

- HTML выкладывается в `docs/{project}/`

## Рентген текста (X-ray Mode)

Независимый режим анализа любого продающего текста. Не привязан к стейт-машине и проектам.

### Активация
Команда: `"Рентген — {текст или путь к файлу или URL}"`

Примеры:
- `"Рентген — [вставленный текст]"`
- `"Рентген — projects/nutriciologia/final.md"`
- `"Рентген — projects/nutriciologia/draft.md"` (анализ незавершённого текста)
- `"Рентген — https://example.com/landing-page"` (анализ внешнего сайта)

### Протокол

#### Для текста / файла
1. Загрузи блоки 01 + 10
2. Определи формат текста (Landing / Email / Ad / VSL / Chatbot)
3. Выполни полный анализ по протоколу [XRAY_PROTOCOL_V2] из блока 10
4. Выведи отчёт в формате [XRAY_OUTPUT_V2]

#### Для URL (внешний сайт)
1. Загрузи блоки 01 + 10
2. Используй инструмент WebFetch для загрузки страницы. Prompt для WebFetch:
   `"Извлеки весь продающий текст со страницы. Убери навигацию, футер, cookie-баннеры, меню. Сохрани структуру: заголовки, подзаголовки, буллеты, CTA-кнопки, отзывы, FAQ. Верни чистый текст с сохранением иерархии."`
3. Если страница слишком большая или WebFetch не смог извлечь контент — сообщи пользователю и предложи вставить текст вручную
4. Определи формат текста (Landing / Email / Ad / VSL / Chatbot)
5. Выполни полный анализ по протоколу [XRAY_PROTOCOL_V2] из блока 10
6. Выведи отчёт в формате [XRAY_OUTPUT_V2]

### Сохранение
- Текст из проекта → сохрани отчёт в `projects/{name}/xray.md`
- Внешний текст (вставленный) → выведи отчёт в чат (без сохранения)
- Внешний URL → сохрани отчёт в `xrays/{slug}.md` (slug = домен + путь, например `example-com-landing`)

### Коммит (если сохранён файл)
Формат: `xray({проект или slug}): {краткое описание — балл и ключевая находка}`
Примеры:
- `xray(nutriciologia): 72/100 — weak mechanism, strong lead`
- `xray(example-com-landing): 65/100 — no social proof, strong lead`

### HTML-рентген (автосборка)

После сохранения `xray.md` (в проект или в `xrays/`):

1. Спроси: **"Собрать HTML-рентген для GitHub Pages?"**
2. Если да — выполни:
   ```bash
   # Для проектного рентгена:
   python scripts/build_xray.py {project_slug} --input xray.md
   # Для внешнего рентгена:
   python scripts/build_xray.py {slug} --input xray.md --source xrays
   ```
3. Результат: `docs/{project_or_slug}/xray.html`
4. Коммит: `xray({project_or_slug}): build HTML report`

Шаблон: `templates/xray.html` (Jinja2 + встроенный CSS, тёмная тема)
Скрипт: `scripts/build_xray.py`

## База знаний

### Архитектура

Knowledge base работает через **локальную эмбеддинг-модель** (мини-нейросеть):
- Модель: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
- Каждый чанк текста прогоняется через эту нейросеть и превращается в **вектор** (384 числа), кодирующий смысл текста
- Векторы хранятся в ChromaDB (`chroma_data/`)
- При поиске запрос тоже превращается в вектор, и ChromaDB находит чанки с ближайшими по смыслу векторами
- Это **семантический поиск** — ищет по смыслу, а не по ключевым словам. Запрос "лекарство от рака" найдёт и "исцеление опухоли", и "уничтожить раковые клетки"

### MCP-инструменты

Для доступа к knowledge/ используй MCP-инструмент `search_knowledge`:
- `search_knowledge(query, n_results=5, category=None)` — семантический поиск
- `list_sources()` — список файлов в базе
- `reindex()` — переиндексация после добавления файлов

Категории (параметр `category`):
- `formulas` — формулы заголовков, лидов, CTA
- `examples` — референсные продающие тексты
- `expert` — материалы эксперта (транскрипты, статьи)
- `audience` — отзывы, комментарии, опросы

Правило: после добавления новых файлов в knowledge/ вызови `reindex()`.

### Стратегия семантического поиска

**Правила эффективного поиска:**

1. **Используй описательные фразы, а не ключевые слова.**
   - Плохо: `"заголовок"`
   - Хорошо: `"формула написания заголовка с конкретной цифрой и обещанием"`

2. **Один запрос = одна тема.** Не смешивай несколько тем в одном запросе. Лучше сделать 3 отдельных поиска.

3. **Для широкого охвата — увеличь n_results** (до 20). Для точечного ответа — оставь 3-5.

4. **Фильтруй по category**, когда знаешь, где искать:
   - Ищешь формулу → `category="formulas"`
   - Ищешь пример текста → `category="examples"`
   - Ищешь данные об аудитории → `category="audience"`

5. **Для анализа по конкретному файлу** — используй прямой доступ к ChromaDB с `where={"source": "path/to/file.md"}`.

6. **Мульти-ракурсный поиск.** Чтобы извлечь Big Idea или полную картину, делай несколько запросов с разных углов:
   - `"главное обещание результат трансформация"` — что обещают
   - `"уникальный механизм секрет метод система"` — как это работает
   - `"угроза опасность кризис предупреждение"` — от чего спасают
   - `"открытие исследование учёные доказали"` — на чём основано
   - `"шокирующая правда скрывают замалчивают"` — какой хук

7. **Язык запроса = язык документов.** База мультиязычная, но лучшие результаты — когда запрос на том же языке, что и текст.

### Конвертация PDF → Markdown

Для добавления PDF в базу знаний:

1. Извлеки текст через `pdfplumber` (Python):
   ```python
   import pdfplumber
   with pdfplumber.open("file.pdf") as pdf:
       for page in pdf.pages:
           text = page.extract_text()
   ```

2. Сохрани как `.md` в нужную подпапку `knowledge/`

3. Вызови `reindex()` для индексации

**Pandoc** (для конвертации между форматами, но НЕ из PDF):
- Путь: `/Library/Frameworks/Python.framework/Versions/3.11/lib/python3.11/site-packages/pypandoc/files/pandoc`
- Версия: 3.8.2.1
- Установлен через `pypandoc` (pip)
- Pandoc НЕ читает PDF, только создаёт. Для PDF → text используй `pdfplumber`.

## Режим ресерча

При команде **"Режим ресерча"** — прочитай `CLAUDE_RESEARCH.md` и работай по его инструкциям.
- Блоки: `research-engine/blocks/`
- Проекты: `research-engine/projects/`
- Агенты: `research-engine/blocks/agents/`
- Стейт-машина: INPUT → COLLECTION → SYNTHESIS → SIMULATION → VALIDATION → DELIVERY
- Выход: секционный `research_pack/` (11 файлов)

Research Engine — автономная система маркетинговых исследований. Работает независимо от Copycraft. На выходе даёт готовый датасет, который можно передать в Copycraft как INPUT или использовать как самостоятельный продукт.

## Ключевые запреты

1. Не придумывай факты, цифры, кейсы — только из источников или подтверждённые пользователем
2. Не пиши текст до утверждения STRATEGY
3. Не выдавай весь материал одним сообщением без команды "Собери финал"
4. Не переходи в DELIVERY без PASS по всем обязательным блокам
5. Не игнорируй Evidence Map при нехватке данных
6. Результаты поиска показывай пользователю ПЕРЕД вставкой в текст
7. Не вставляй один и тот же proof-элемент (кейс/отзыв/стат) полностью в 2+ блоках — используй Proof Usage Registry для anti-repetition
