# Copycraft — AI-ассистент для создания продающих текстов

## Что это

Приложение, которое помогает копирайтеру пошагово создавать высоконверсионные продающие тексты для лендингов, продажи услуг и информационных продуктов.

Работает как интерактивный диалог: пользователь задает продукт и сегмент, а система — блок за блоком — ведет его через весь процесс написания текста, от сбора контекста до финальной версии.

Ключевой принцип: один сегмент, одна проблема, один уникальный механизм, одно решение.

## Для кого

- Копирайтеры, которые пишут продающие тексты для онлайн-продуктов и услуг
- Эксперты, которые хотят самостоятельно создавать тексты для своих лендингов
- Маркетологи, которым нужно быстро генерировать конверсионные тексты

## Стейт-машина: этапы создания текста

Текст создается через 8 стейтов с ветвлениями и циклами. Система всегда явно указывает текущий STATE в начале ответа.

### Схема переходов

```
INPUT → QUERY ──────────────────┐
  │                              │
  ├─ (достаточно данных) ────────┼──→ STRATEGY → EXECUTION ⇄ DEBUGGING
  │                              │                              │
  └─ (Авто-ресерч) → RESEARCH ──┘                      (PASS, все блоки)
                                                               │
                                                           DELIVERY → REVIEW
```

### Правила переходов

- **INPUT → QUERY** — если данных мало (MISSING ≥ 3), система задаёт 3–7 уточняющих вопросов
- **INPUT → STRATEGY** — если данных достаточно, QUERY пропускается. STRATEGY включает: стратегия v1 (без KB) → KB GATE → стратегия v2 (с KB) → выбор → STRATEGY CRITIC
- **INPUT → RESEARCH** — если пользователь выбрал "Авто-ресерч"
- **EXECUTION → DEBUGGING** — обязательный цикл после каждого блока текста
- **DEBUGGING → EXECUTION** — если блок не прошёл проверку (FAIL), возврат на исправление
- **DEBUGGING → DELIVERY** — только когда все обязательные блоки утверждены (status=APPROVED)
- **DELIVERY → REVIEW** — итеративные правки по запросу пользователя

### Детали каждого стейта

| # | Стейт | Что происходит | Выход | Решения пользователя |
|---|-------|---------------|-------|---------------------|
| 1 | **INPUT** | Разбор запроса: 3–7 строк — что система поняла, список недостающих полей | Evidence Map (факты, гипотезы, пробелы) | Выбрать режим: "Короткий бриф" или "Авто-ресерч" |
| 2 | **QUERY** | 3–7 вопросов для заполнения пробелов. Без копирайтинга, без CTA | Ответы пользователя пунктами 1–7 | Ответить на вопросы |
| 3 | **RESEARCH** | Полный ресерч через JTBD-декодер. Фокус: мотивация, барьеры, альтернативы, язык клиента | JTBD Map + Findings + Assumptions + Missing + Sources + ETS (DRE→DES) | Подтвердить/скорректировать находки |
| 4 | **STRATEGY** | Двойная стратегия: PHASE A (без KB) → KB GATE (search_knowledge) → PHASE B (с KB) → выбор 1 или 2 → STRATEGY CRITIC (7 вопросов, PASS/FAIL) | Strategy Skeleton (v1 и v2) | Выбрать стратегию 1 или 2 |
| 5 | **EXECUTION** | Генерация текста через RMBC. Две фазы: PHASE B (BRIEF — каркас) → PHASE C (COPY — текст). Один блок за сообщение | Утверждённые блоки текста | Утвердить BRIEF, затем — каждый блок по отдельности |
| 6 | **DEBUGGING** | Проверка блока: PASS/FAIL. При FAIL — 1–3 правки в формате "Причина → Правка" | Статус блока (APPROVED / на доработку) | Принять блок / запросить правки / перейти к следующему |
| 7 | **DELIVERY** | Сборка финала из утверждённых блоков. FINAL SELF-CHECK (5 пунктов). Новые смыслы запрещены | Готовый текст | Подтвердить финал |
| 8 | **REVIEW** | Точечные правки: до 10 правок + 3 предложения A/B-тестов. Confidence (Высокая/Средняя/Низкая) | Улучшенная версия | Принять правки или запросить ещё |

### Правила EXECUTION (подробно)

**Атомарность:** в одном сообщении допускается только ОДНА фаза — либо BRIEF, либо COPY. DEBUGGING — только в следующем сообщении.

**PHASE B — BRIEF (каркас):**
1. Тип лида (по Awareness Level)
2. Порядок блоков: Lead → Story → Mechanism → Product Reveal → Offer → Proof → Close
3. Расстановка Mini-Proof
4. MOS BOOSTERS PLAN (зависит от MOS_MODE):
   - **MODE A:** Offer Stack (Guarantee + Price Framing + Scarcity)
   - **MODE B:** Headline (curiosity + Big Idea), Bullets (micro-belief shifts), Proof (CPB stacking)
   - **MODE C:** ETS (DRE→DES), Story arc + belief shifts, Proof (story-proof + social proof)
5. SELF-CHECK (3 пункта): какие факты, что гипотеза, что нельзя утверждать
6. Контрольный вопрос: "Утвердить BRIEF? (да/правки)"

**PHASE C — COPY (текст):**
- Генерация только после утверждения BRIEF
- Один блок RMBC за сообщение (Lead / Story / Mechanism / Product Reveal / Offer+Close)
- После каждого блока: STOP → "Следующий блок? (да/правки/собери финал)"

**RESEARCH-MINI (внутри EXECUTION):**
Если перед созданием блока обнаружена нехватка данных — мини-ресерч (максимум 1 итерация на блок). Три варианта: вопрос пользователю, поиск в источниках, поиск в Knowledge-файлах.

### Запреты по стейтам

- В QUERY / RESEARCH / STRATEGY запрещены CTA, кнопки, P.S. и любые "продающие" блоки
- Запрещено выдавать весь текст одним сообщением без команды "Собери финал"
- Запрещено придумывать Proof / цифры / кейсы — только подтверждённые факты
- Запрещено переходить в DELIVERY без утверждения всех обязательных блоков

## Evidence Map — обязательный промежуточный вывод

Перед переходом к написанию текста система обязана вывести Evidence Map — структурированную карту того, что известно, что предполагается и чего не хватает.

### Когда выводить

- Всегда в конце STATE=INPUT
- Всегда в конце STATE=RESEARCH
- Перед STATE=STRATEGY, если есть хоть одно допущение
- Перед STATE=EXECUTION, если источники/факты не показаны

### Формат Evidence Map

```
1) FACTS (что точно известно)
   - F1: ...
   - F2: ...

2) SOURCES (откуда это взято)
   - S1: <название документа / страница / ссылка>
   - S2: ...

3) INFERENCES (что логически следует из фактов)
   - I1: ...
   - I2: ...

4) HYPOTHESES (что НЕ подтверждено)
   - H1: ... (почему это гипотеза)
   - H2: ...

5) MISSING INFO (что критично не хватает)
   - M1: ...
   - M2: ...

6) NEXT ACTION (выбор следующего шага)
   A) QUERY: задам 3–7 вопросов
   B) RESEARCH: включить авто-ресерч
   C) STRATEGY: данных достаточно — строю стратегию
```

### Правило простоты

- Если MISSING INFO <= 2 пункта → не больше 3 вопросов, переход к STRATEGY
- Если MISSING INFO > 2 → предложить "Авто-ресерч"

## Блоки текста (RMBC-скелет)

Любой продающий текст строится по архитектуре RMBC (Research → Mechanism → Brief → Copy). Фазы R и M покрываются стейтами RESEARCH и STRATEGY. Фазы B и C — это EXECUTION.

### Базовый скелет блоков

| # | Блок | Обязательный | Описание |
|---|------|-------------|----------|
| 1 | **Lead** (Вступление) | Да | Заголовок + подзаголовок + вступительный текст. Тип лида выбирается по Awareness + Sophistication (см. Lead Router ниже). Первое предложение — макс 12 слов. Ритм: чередование коротких и длинных абзацев. |
| 2 | **Story** (Background) | Да | История в 3 актах: (1) «Тебе было хуже» — момент провала, (2) Точка перелома — инсайт, (3) Первый результат — Proof of Concept. Макс 300 слов. Начинай с дна, не раскрывай Механизм полностью. |
| 3 | **Mechanism** | Да | Два подблока: **UMP** (Механизм Проблемы — почему стандартный подход не работает) + **UMR** (Механизм Решения — 3–5 шагов, как это работает). Простота, визуальность, логика, доказуемость. |
| 4 | **Product Reveal** | Да | Отдельный от оффера блок: представление продукта как системы для внедрения UMR. Формула: «Чтобы вы могли внедрить [UMR] без ошибок, мы создали [продукт]». Включает: название, что внутри, путь клиента, поддержка. |
| 5 | **Offer + Close** | Да | Value Stack (стоимость каждого элемента) + реальная цена + рассрочка + бонусы (3–5, каждый с ценой). Элементы срочности (минимум 2): временной, количественный, социальный. |
| 6 | **Гарантия** | **Да** | Risk reversal: снятие риска покупки. Возврат, пробный период, гарантия результата. Обязательный блок (ранее был опциональный). |
| 7 | **P.S.** | **Да** | 2–3 штуки: (1) Усиление гарантии, (2) Цена бездействия, (3) Бонус за скорость. Обязательный блок (ранее был опциональный). Всегда заканчивать кнопкой + P.S. |

Правило Mini-Proof: если Awareness ≤ Solution Aware или Sophistication ≥ Stage 3 → вставить Proof ДО Offer.

### Lead Router — выбор типа лида

| Awareness + Sophistication | Тип лида | Описание |
|---------------------------|----------|----------|
| Низкая осведомлённость | Problem-Agitate | Описать боль, усилить, намекнуть на выход |
| Solution Aware | Solution Bridge | «Вы уже пробовали X, но есть другой путь...» |
| Высокая искушённость | Mechanism-First | Начать с нового механизма / Big Idea |
| Product Aware + скепсис | Proof-First | Начать с доказательства / кейса |
| Most Aware | Offer-First | Сразу оффер: цена, бонус, дедлайн |

### Правила генерации блоков

- Каждый блок генерируется по отдельности — один блок за сообщение
- Перед генерацией — ЛИД-ПЛАН: Уровень [X] | Тип [Story/Problem/Secret/Offer] | Ключевые элементы
- После каждого блока — обязательный DEBUGGING (PASS/FAIL)
- Запрещено выдавать весь текст одним сообщением без команды "Собери финал"
- Запрещено придумывать Proof/цифры/кейсы — только подтверждённые факты

## Двухосевой анализ рынка

Система определяет координаты клиента по двум осям — Awareness (осведомлённость) и Market Sophistication (искушённость рынка). Пересечение осей определяет MOS_MODE — операционный режим генерации текста.

### Ось 1: Awareness Level (5 уровней по Шварцу)

| Уровень | Состояние клиента | Тип лида | Что можно говорить |
|---------|-------------------|----------|-------------------|
| **1. Unaware** | "У меня всё хорошо" | Story-Lead или Secret-Lead | Нельзя говорить о продукте/проблеме напрямую |
| **2. Problem Aware** | "У меня болит, но не знаю чем лечить" | Problem-Solution Lead | Назвать проблему, усилить боль, показать решение |
| **3. Solution Aware** | "Знаю, что есть массаж, таблетки и йога" | Secret System Lead | Доказать, что ВАШ механизм лучше |
| **4. Product Aware** | "Знаю вашу компанию, но дорого" | Offer Lead | Убеждение, оффер, снятие возражений |
| **5. Most Aware** | "Куда платить?" | Direct Offer | Только оффер: цена, бонус, дедлайн |

### Ось 2: Market Sophistication (5 стадий)

| Стадия | Состояние рынка | Стратегия |
|--------|----------------|-----------|
| **1. Pioneer** (девственный рынок) | Первые игроки, нет конкуренции | Просто скажите, что делает продукт |
| **2. Claim** (расширение) | Появляются конкуренты | Расширить обещание: быстрее, безопаснее, проще |
| **3. Mechanism** | Обещания исчерпаны | Ввести Уникальный Механизм ("формула X") |
| **4. Elaborated** (расширение механизма) | Механизмы копируют | Усилить до Большой Идеи (Big Idea) |
| **5. Identification** (мёртвый рынок) | Аудитория всё видела | Идентификация, стиль жизни, ценности |

### MOS_MODE — операционный режим (результат пересечения осей)

| Режим | Когда применять | Что меняется |
|-------|----------------|-------------|
| **MODE A: DIRECT OFFER** | Soph 1–2 или Awareness = Product/Most | Прямые обещания. Offer Stack обязателен (Guarantee + Price Framing + Scarcity). Big Idea опциональна. |
| **MODE B: MECHANISM / BIG IDEA** | Soph 3–4 или Awareness = Problem/Solution | Уникальный механизм в центре. Headline (curiosity + Big Idea), Bullets (micro-belief shifts), Proof (CPB stacking). |
| **MODE C: IDENTITY / STORYSELLING** | Soph 4–5, усталый рынок, высокий скепсис | Идентификация и эмпатия. ETS (DRE→DES), Story arc + belief shifts, прокурорская аргументация (objection-first). |

### Алгоритм выбора

1. Определи Awareness → выбери структуру Lead
2. Определи Sophistication → определи нужна ли Big Idea
3. Выбери MOS_MODE (A / B / C) на пересечении
4. Сформулируй стратегию одним предложением

## JTBD-фреймворк (анализ аудитории)

Вместо простого "боль / желание" система использует структурированный анализ по Jobs To Be Done. Клиент не покупает продукт — он "нанимает" его для выполнения конкретной работы.

### Принцип: смерть соцдема

Запрещено опираться только на "Женщина, 35 лет". Один продукт "нанимают" для разных работ:
- Работа 1: Получить повышение (Жадность / Статус)
- Работа 2: Помогать ребенку, не чувствовать себя плохой матерью (Страх / Любовь)
- Работа 3: Смотреть сериалы в оригинале (Развлечение / Комфорт)

Всегда спрашивать: **"На какую РАБОТУ клиент нанимает продукт?"**

### 4 силы покупки (The 4 Forces)

| Сила | Вопрос | Роль в тексте |
|------|--------|--------------|
| **PUSH (Толчок)** | "Почему мне плохо сейчас?" | Боль текущего момента. Описывать момент максимального раздражения (Agitation). |
| **PULL (Тяга)** | "Как будет хорошо потом?" | Картинка лучшего будущего. Продавать трансформацию, а не функции. |
| **ANXIETY (Тревога)** | "А вдруг не получится?" | Страхи перед покупкой. Закрывать через Гарантии, Отзывы и Механизм. |
| **HABIT (Привычка)** | "Может, и так сойдет?" | Инерция. Показывать цену бездействия (Cost of Inaction). |

### Архетипы проблем

| Архетип | Тон текста |
|---------|-----------|
| Острая боль (Bleeding Neck) | Срочность, директивность |
| Хроническая боль (Chronic Pain) | Эмпатия, надежда |
| Скрытая угроза (Looming Threat) | Предупреждение, авторитет |
| Стремление к удовольствию (Desire for Gain) | Вдохновение, статус |

### JTBD Map (выход STATE=RESEARCH)

При проведении ресерча система формирует JTBD Map:
- **JOB-TO-BE-DONE** — одна строка: на какую работу нанимают продукт
- **CONTEXT / TRIGGER** — когда возникает потребность
- **DESIRED OUTCOME** — что хочет получить / почувствовать
- **BARRIERS / ANXIETIES** — почему не делает
- **CURRENT ALTERNATIVES** — что пробовала / чем заменяет
- **LANGUAGE** — 5–10 фраз "словами клиента"

## Критерии качества

Двухуровневая система: формальные метрики (автоматические) + смысловой Critic Mode (13 пунктов).

### Уровень 1: Формальные метрики

| Критерий | Как проверяется | Порог |
|----------|----------------|-------|
| **Разговорность** | Средняя длина предложения | Не более 15 слов |
| **Разговорность** | Доля предложений с "вы/ты/ваш" | Не менее 30% |
| **Конкретность** | Наличие цифр, сроков, фактов | Минимум 1 на блок |
| **Читаемость** | Нет абзацев длиннее 4 строк | 100% |
| **Единый сегмент** | Текст обращается к одному типу читателя | Ручная проверка пользователем |
| **Без клише** | Отсутствие фраз из стоп-листа | 0 совпадений |

### Уровень 2: Смысловой Critic Mode (13 пунктов)

Запускается автоматически в STATE=DEBUGGING после каждого блока. Текст не показывается пользователю, пока не пройдёт Critic Mode.

| # | Вопрос | Если "нет" |
|---|--------|-----------|
| 1 | Есть ли конкретная боль из JTBD, а не общие слова? | Переписать с опорой на JTBD Map |
| 2 | Раскрыт ли УМ Проблемы (почему раньше не работало)? | Добавить UMP |
| 3 | Есть ли УМ Решения с названием и объяснением? | Добавить UMR |
| 4 | Соответствует ли Лид уровню осведомленности Шварца? | Сменить тип лида |
| 5 | Есть ли Большая Идея (если рынок перенасыщен)? | Добавить Big Idea (для Soph 3+) |
| 6 | Есть ли Value Stack с цифрами? | Добавить Value Stack |
| 7 | Гарантия снимает главный риск? | Переработать гарантию |
| 8 | Язык живой, без корпоративного жаргона? | Переписать разговорным языком |
| 9 | Есть ли срочность (2+ триггера)? | Добавить элементы срочности |
| 10 | Каждое предложение ведет к следующему? | Проверить логические переходы |
| 11 | Использованы ли данные из RESEARCH (JTBD map, VOC-фразы, DRE/DES, барьеры)? | Вернуться к research.md, встроить данные. Если RESEARCH пропущен — пометить гипотезы [ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ] |
| 12 | Учтены ли формулы/примеры из knowledge/? | Консультировать KB. Если недоступна — зафиксировать причину |
| 13 | Jargon-check: все термины понятны ЦА без гугления? | Заменить специализированные термины на простые аналоги или добавить пояснение |

### Launch Checklist (перед DELIVERY)

Все 10 вопросов должны быть "Да". Если хоть один "Нет" — доработать перед финальной сборкой:

1. ЦА четко определена через JTBD?
2. Уровень Шварца выбран правильно?
3. UMP снимает вину с клиента?
4. UMR имеет название и 3 шага объяснения?
5. Большая Идея пробивает рекламную слепоту?
6. Оффер бьет в текущую боль, за которую платят сейчас?
7. Value Stack в 3–5 раз превышает цену?
8. Гарантия покрывает главный риск клиента?
9. Есть 2+ триггера срочности?
10. Язык звучит как разговор двух людей?

## Truth & Proof Protocol

Протокол безопасности смыслов — система защиты от пустых обещаний, фальшивой эмпатии и необоснованных заявлений.

### 1. Fluff Filter (Фильтр "Анти-вода")

Стоп-лист расширен до концепции: если фразу можно применить к конкуренту, не меняя ни слова — это мусор.

| Запрещено | Заменить на |
|-----------|------------|
| "Высокое качество" | Конкретные характеристики, цифры |
| "Инновационный / Революционный" | Описание Уникального Механизма |
| "Эффективный / Успешный" | Кейс, цифра, результат "До / После" |
| "Индивидуальный подход" | Описание процесса диагностики |
| "Команда профессионалов" | Опыт в годах, регалии, имена |

### 2. Proof Burden (4 типа доказательств)

Любое обещание в тексте должно быть подкреплено хотя бы одним типом доказательства:

1. **Логическое** — объяснение механизма (почему это работает)
2. **Социальное** — отзывы, рейтинги, кейсы клиентов
3. **Демонстрация** — видео, скриншоты, "До / После"
4. **Авторитет** — эксперты, сертификаты, исследования

### 3. Claim Calibration (калибровка обещаний по рынку)

| Уровень рынка | Допустимый тон обещаний |
|--------------|------------------------|
| "Наивный" (Soph 1–2) | Можно "Быстрый результат" |
| "Циничный" (Soph 4–5) | "Понятный, логичный, безопасный путь" |

Всегда оценивать: не звучит ли оффер "Too Good To Be True"?

### 4. Запрет фальшивой эмпатии

Вместо "Я понимаю вашу боль" — **описать** боль детально.
- Плохо: "Вы, наверное, устали от диет."
- Хорошо: "Вы смотрите в зеркало и обещаете себе, что с понедельника всё изменится. Но наступает среда, стресс на работе, и рука сама тянется к сладкому."

### 5. Треугольник релевантности

Любой смысл в тексте проверяется по 3 углам:
1. **Продукт:** Это правда? Продукт действительно это делает?
2. **Аудитория / JTBD:** Им это важно?
3. **Рынок:** Это звучит свежо?

## Формат входных данных

### Как загружать материалы

| Тип данных | Форматы | Как система распознает |
|-----------|---------|----------------------|
| **Формулы и шаблоны** | `.md` | Файлы в `knowledge/formulas/`. Могут быть большими — релевантные фрагменты находятся через RAG. |
| **Примеры текстов** | `.md` | Файлы в `knowledge/examples/`. Система анализирует структуру и выделяет паттерны. |
| **Материалы эксперта** | `.md` | Файлы в `knowledge/expert/`. Транскрипты вебинаров, интервью, статьи эксперта. |
| **Данные аудитории** | `.md` | Файлы в `knowledge/audience/`. Отзывы, комментарии, результаты опросов. |

### Структура рабочего пространства

```
copycraft/
  knowledge/          — база знаний (доступ через MCP search_knowledge)
    formulas/         — формулы и шаблоны копирайтинга
    examples/         — референсные продающие тексты
    expert/           — материалы эксперта (транскрипты, статьи)
    audience/         — данные об аудитории
  projects/           — проекты (каждый в своей папке)
    {name}/
      state.md        — текущий стейт и прогресс
      brief.md        — заполненная карточка проекта
      strategy.md     — выбранная стратегия
      draft.md        — черновик (блок за блоком)
      final.md        — финальная версия
      results.md      — метрики и A/B тесты
  scripts/            — MCP-сервер и утилиты
  blocks/             — модульные инструкции (9 блоков)
```

### Правила загрузки

- Формат файлов — `.md` (markdown). Конвертируйте другие форматы перед загрузкой
- Видео и аудио не поддерживаются напрямую — нужно загружать транскрипты
- После добавления файлов в `knowledge/` вызовите `reindex()` для индексации

## Внешний ресерч

### Что ищет система

- Отзывы и комментарии ЦА (форумы, соцсети, маркетплейсы)
- Тексты конкурентов (лендинги, рекламные посты)
- Статистика и исследования по нише

### Ограничения и валидация

| Проблема | Решение |
|----------|---------|
| Мусорные результаты | Система показывает найденное пользователю ПЕРЕД использованием. Пользователь отмечает галочками, что использовать. |
| Устаревшие данные | Система проверяет дату публикации. Данные старше 2 лет помечаются как "⚠ возможно устарело". |
| Нерелевантные источники | Приоритет: русскоязычные источники → англоязычные. Пользователь может указать конкретные сайты для поиска. |
| Ложные факты/цифры | Система НЕ вставляет найденные цифры в текст автоматически. Только предлагает — пользователь подтверждает. |

### Режимы ресерча

- **Автоматический** — система ищет сама на стейтах "Ресерч" и "Доказательства"
- **По запросу** — пользователь просит найти конкретное ("найди статистику по рынку нутрициологии в РФ")
- **Выключен** — пользователь работает только с загруженными данными

## Дополнительные функции

### История проектов

- Каждый завершённый проект сохраняется с полным контекстом: бриф, стратегия, все блоки, выбранные варианты
- При создании нового проекта в той же нише — система предлагает "Использовать наработки из проекта X?"
- Поиск по прошлым проектам: по нише, сегменту, типу продукта

### Версионность

- Каждый блок сохраняет все сгенерированные варианты (не только выбранный)
- Пользователь может вернуться к любому варианту: "верни второй вариант заголовка"
- История изменений: кто изменил (система/пользователь), когда, что именно
- При возврате на предыдущий стейт — автоматическое создание новой версии

### Экспорт

| Формат | Что включает |
|--------|-------------|
| **Markdown** (`.md`) | Чистый текст, готовый к копированию |
| **PDF** | Отформатированный текст с разбивкой по блокам |
| **Google Docs** | Экспорт через API, с сохранением форматирования |
| **HTML** | Для вставки на лендинг напрямую |
| **Буфер обмена** | Быстрое копирование отдельного блока или всего текста |

### Мульти-формат (поддерживаемые типы текстов)

Помимо лендингов, система поддерживает дополнительные форматы. Все форматы используют ту же стейт-машину и RMBC-скелет, но адаптируют структуру блоков.

| Формат | Описание | Детали см. |
|--------|----------|-----------|
| **Лендинг** | Основной формат. Полный RMBC-проход | Блок 07 |
| **Email-цепочки** | 5 писем: Разогрев → Боль → Механизм → Продукт+Оффер → Close. По 400 слов, каждое письмо = один тип лида | Блок 08 |
| **Ads (Креативы)** | 50–150 слов. Заголовок + подзаголовок + текст + CTA. Шаблоны по платформам (VK, FB, Яндекс.Директ, Telegram). Адаптация: холодный / тёплый / ретаргетинг | Блок 08 |
| **VSL** | 15-минутный видеоскрипт: Лид (0–1:30) → История+UMP (1:30–4:00) → UMR (4:00–8:00) → Продукт (8:00–10:00) → Оффер (10:00–13:00) → Close (13:00–15:00) | Блок 08 |
| **Chatbot** | 7-шаговый диалог: Хук → 3 вопроса → Мини-диагноз (UMP→UMR) → Персональный оффер → Close. 1 факт на сообщение | Блок 08 |

### Работа с несколькими сегментами

Один продукт — несколько сегментов аудитории:

1. **Создание базового текста** — полный цикл для основного сегмента
2. **Адаптация** — система берет готовый текст и предлагает изменения для нового сегмента:
   - Что оставить как есть
   - Что переписать (лид, история, возражения — зависят от сегмента)
   - Что добавить/убрать
3. **Независимая версия** — сохраняется отдельно, со своим брифом и стратегией
4. Пользователь может выбрать: адаптировать существующий текст или написать с нуля

## Пример сценария использования

1. Пользователь пишет: "Создай продающий текст для лендинга. Продукт — курс по нутрициологии"
2. **STATE=INPUT:** система анализирует запрос, выводит Evidence Map (что известно, что не хватает). Предлагает режим: "Короткий бриф" или "Авто-ресерч".
3. **STATE=QUERY:** система задаёт 5 вопросов (JTBD, боли, конкуренты, механизм, гарантии). Пользователь отвечает.
4. **STATE=RESEARCH:** JTBD Map + Findings + Sources + ETS (DRE→DES). Пользователь подтверждает находки.
5. **STATE=STRATEGY:** Awareness = Solution Aware, Sophistication = 3, MOS_MODE = B. Big Idea + Unique Mechanism. Пользователь утверждает стратегию.
6. **STATE=EXECUTION (BRIEF):** каркас текста — тип лида, порядок блоков, MOS Boosters Plan. Пользователь утверждает.
7. **STATE=EXECUTION (COPY):** блок за блоком — Lead → DEBUGGING → Story → DEBUGGING → Mechanism → DEBUGGING → Product Reveal → DEBUGGING → Offer+Close → DEBUGGING.
8. **STATE=DELIVERY:** сборка финала из утверждённых блоков. FINAL SELF-CHECK.
9. **STATE=REVIEW:** точечные правки, A/B-предложения. Экспорт в нужный формат.
